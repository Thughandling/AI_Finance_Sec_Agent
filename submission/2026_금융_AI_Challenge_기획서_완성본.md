## 1. 아이디어 핵심 요약

보이스피싱 피해자는 통화 중 심리적 압박을 받으면서 동시에 송금을 요구받는다. 그러나 현재의 거래 이상탐지, 통화 경고, 예방 교육은 각각 분리되어 있어 고객이 송금 직전 “왜 위험한지”와 “지금 무엇을 해야 하는지”를 한 번에 이해하기 어렵다.

AI_Finance_Sec는 의심 통화 내용과 평소와 다른 거래 신호를 함께 살펴 위험 이유를 설명하고, 송금 중단·공식 번호 재확인·피해 발생 시 1394 통합신고, 긴급한 범죄 신고 112, 해당 금융회사 지급정지 요청 등 단계별 행동을 안내한다. 최초 도입 지점은 은행 모바일 앱의 송금 확인 단계이며, 향후 상담원과 이상금융거래탐지 운영 화면으로 확장한다.

고객에게는 피해 직전 판단을 되찾을 시간을 제공하고, 금융회사에는 기존 이상거래 경고를 고객이 이해하고 행동할 수 있는 안내로 전환하는 고객보호 수단을 제공한다. 현재 MVP는 합성 시나리오로 서비스 경험과 설명 방식을 검증하는 단계이며, 실제 피해 예방 효과는 금융회사 POC에서 별도 측정한다.

## 2. 문제 정의 및 제안 배경

### 2.1 피해 규모가 크고 수법 변화가 빠르다

[경찰청 자료](https://www.police.go.kr/user/bbs/BD_selectBbs.do?q_bbsCode=1007&q_bbscttSn=20260526143737248&q_currPage=1&q_rowPerPage=12&q_sortName=&q_sortOrder=&q_tab=)에 따르면 보이스피싱 피해액은 2024년 상반기 3,243억 원에서 2025년 상반기 6,421억 원으로 98.1% 증가했다. 범정부 대책 이후 2026년 1~4월 피해액은 전년 같은 기간보다 48% 감소했지만 여전히 2,225억 원 규모다. 대응 성과가 나타나고 있어도 지속적인 탐지와 고객 행동 전환이 필요한 이유다.

### 2.2 피해의 결정적 순간에 정보가 분리돼 있다

전형적인 피해 과정은 다음과 같다.

1. 수사기관·금융회사·가족 등을 사칭한 연락이 고객을 심리적으로 고립시킨다.
2. 공격자는 긴급성·보안·비밀유지를 강조하며 공식 확인을 방해한다.
3. 고객은 통화를 유지한 채 신규 수취인이나 평소보다 큰 금액으로 송금한다.
4. 피해를 인지한 뒤에도 신고·금융회사 연락·지급정지 요청 순서를 몰라 골든타임을 잃는다.

통화 내용은 위험하지만 거래만 보면 평범할 수 있고, 거래는 이상하지만 고객이 이미 공격자의 설명을 신뢰하면 단순 경고를 무시할 수 있다. 따라서 통화 맥락과 거래 신호를 결합하고, 고객이 이해할 수 있는 이유와 행동을 동시에 제공해야 한다.

### 2.3 기존 대응의 공백

| 기존 대응 | 강점 | 남아 있는 공백 |
|---|---|---|
| 은행 FDS·거래 문진 | 이상거래를 탐지하고 거래를 확인 | 통화에서 형성된 기망 맥락과 고객의 심리 상태를 충분히 설명하기 어려움 |
| 통화·문자 경고 서비스 | 의심 번호·문구를 빠르게 경고 | 실제 송금 신호와 연결되지 않으면 위험의 긴급도를 판단하기 어려움 |
| 예방 교육·캠페인 | 수법과 대응 지식을 넓게 전달 | 피해 직전의 압박 상황에서 즉시 행동으로 이어진다는 보장이 없음 |
| 범용 AI 챗봇 | 자연어 질문에 유연하게 답변 | 금융회사 정책, 공식 행동, 책임 경계가 고정되지 않으면 잘못된 권고 위험이 있음 |

AI_Finance_Sec는 기존 시스템을 대체하지 않는다. 기존 FDS와 기관 정보공유가 탐지한 위험을 고객이 이해하고 실행할 수 있는 행동 안내로 변환하는 **고객 접점 계층**을 제안한다.

## 3. 목표 고객·도입 주체·서비스 채널

### 3.1 1차 사용자

- 의심 통화를 받으면서 모바일뱅킹 송금을 시도하는 금융소비자
- 기관사칭·대출·가족빙자 등의 압박 때문에 공식 확인 절차를 건너뛸 가능성이 높은 사용자
- 피해 이후 신속한 신고와 지급정지 절차를 안내받아야 하는 고객

보이스피싱은 특정 연령층만의 문제가 아니므로 최초 시장을 고령층으로 한정하지 않는다. 다만 금융회사 POC에서는 고령층, 사회초년생, 고액·신규수취인 거래 고객 등 위험 상황별 사용성을 따로 측정한다.

### 3.2 구매·도입 주체

- 금융소비자보호·금융사기대응 조직
- 이상금융거래탐지(FDS) 운영 조직
- 모바일뱅킹·디지털채널 조직
- 콜센터·피해접수 조직

### 3.3 최초 채널

첫 도입 채널은 **은행 모바일 앱의 송금 확인 단계**로 제안한다. 통화 위험과 거래 위험이 만나는 순간이며, 고객이 실제 송금을 완료하기 전에 개입할 수 있기 때문이다. 두 번째 채널은 상담원이 위험 근거와 권장 행동을 함께 확인하는 고객보호 보조 화면이다.

## 4. 서비스 콘셉트와 사용자 여정

### 4.1 한 문장 가치제안

> 의심 통화와 이상거래가 겹치는 순간, 고객이 송금 전에 멈추고 공식 채널로 확인하도록 위험 이유와 다음 행동을 설명한다.

### 4.2 사용자 여정

#### ① 위험 징후 포착

고객이 통화 중 모바일 송금을 시도하면 서비스는 기관 사칭, 비밀유지 요구, 안전계좌 송금 지시 같은 통화 신호와 신규 수취인, 이례적 금액, 통화 직후 거래 같은 거래 신호를 함께 확인한다.

#### ② 이해 가능한 경고

단순히 “위험합니다”라고 표시하지 않고, 고객이 방금 경험한 통화 문장과 거래 변화 중 어떤 요소가 위험 판단에 영향을 줬는지 짧고 명확하게 보여준다.

#### ③ 행동 전환

고객에게 송금을 잠시 멈추고 통화를 종료한 뒤, 앱이나 공식 대표번호를 통해 사실을 다시 확인하도록 안내한다. 실제 거래 제한 여부는 금융회사 정책과 고객 확인 절차에 따른다.

#### ④ 피해 초기 대응

이미 송금한 고객에게는 24시간 보이스피싱 통합신고·상담 번호 1394, 긴급한 범죄 신고 112, 해당 금융회사 연락과 지급정지 요청의 우선순위를 안내한다. 서비스가 신고나 지급정지를 대신 완료했다고 주장하지 않는다. [경찰청의 1394 안내](https://www.police.go.kr/user/bbs/BD_selectBbs.do?q_bbsCode=1007&q_bbscttSn=20260209152732394)를 기준으로 하며, 기관 지침 변경 시 승인 지식을 갱신한다.

#### ⑤ 금융회사 검토

향후 금융회사 운영자는 위험 신호, 고객에게 표시된 설명, 고객의 선택을 확인해 상담과 FDS 정책 개선에 활용한다. 실제 고객 데이터, 이의제기, 감사 기록은 기관 정책과 규제에 맞춰 설계한다.

## 6. 차별성

### 6.1 탐지에서 행동까지 연결한다

AI_Finance_Sec는 통화·거래 탐지 기능과 경쟁하기보다, 탐지 신호가 고객의 송금 재확인과 공식 채널 이동으로 이어지도록 설명과 행동 절차를 더한다.

### 6.2 통화와 거래를 하나의 사건으로 본다

보이스피싱은 대화와 금융거래가 결합된 범죄다. 두 신호를 함께 보아야 위험한 통화 뒤에 이어지는 정상처럼 보이는 송금과, 위험 단어가 포함됐지만 실제로는 송금을 만류하는 정상상담을 구분할 수 있다.

### 6.3 현재 MVP와 향후 생성형 AI 역할을 구분한다

현재 MVP는 Qwen 모델을 실제 호출해 오케스트레이션과 안전 경계를 검증하지만, 모델이 만든 자유문은 고객 화면에 사용하지 않고 서버의 허용된 정책 문장만 표시한다. POC에서는 모델의 구조화된 위험 분석이 오프라인 정확성·안전성 검증을 통과한 경우에만 고객 설명의 보조 입력으로 제한적으로 반영한다. AI가 금융 조치나 최종 행동을 자유롭게 결정하지 않도록 하는 원칙은 두 단계 모두 동일하다.

### 6.4 금융회사 도입을 전제로 한다

독립 앱에서 끝나지 않고 모바일뱅킹, FDS, 콜센터 등 기존 고객보호 체계에 결합되는 구조를 지향한다. 소비자 유료 구독보다 금융회사의 고객보호 기능으로 제공되는 B2B2C 모델이 우선이다.

| 거래 신호 | 신규 수취인, 평소 대비 금액, 통화 직후 거래 등 | MVP는 합성 신호, P2는 기관 승인 데이터 연계 |
| 공식기관 안내를 요약한 데모 지식 | 신고·확인·지급정지 등 행동 순서 | POC에서 기관 검수 후 출처·기준일·승인 상태를 관리하는 지식저장소로 확장 |
| 정상 반례 | “송금할 필요가 없다” 같은 정상상담의 과잉경고 방지 | 정상·위험 균형 검증셋 지속 보강 |

### 7.2 생성형 AI가 필요한 이유

규칙은 알려진 위험 신호를 빠르게 찾을 수 있지만, 공격자가 표현을 바꾸거나 여러 정황이 섞이면 일반화와 설명 작성에 한계가 있다. 현재 MVP의 생성형 AI는 실제 호출·멀티턴·안전 폴백 구조를 검증하는 데 사용하고, 모델 자유문은 폐기한다. 향후에는 구조화된 위험 분석과 설명 초안의 품질이 승인 기준을 통과할 때만 보조적으로 활용한다. 실제 거래 차단, 신고, 지급정지 같은 외부 조치는 어느 단계에서도 모델이 수행하지 않는다.

### 7.3 데이터 확보 원칙

- P0/P1은 개인정보가 없는 합성 데이터로 서비스 흐름을 검증한다.
- 공개 데이터는 이용조건과 라이선스를 확인한 뒤 평가·연구 목적으로 사용한다.
- 실제 금융회사 데이터는 최소수집·비식별·보존기간·접근권한·감사 기준을 기관과 합의한 뒤 사용한다.
- 현재 데모 지식은 공식기관 안내를 요약한 것이며 기관의 별도 승인을 받은 지식저장소가 아니다. POC에서는 기관명, 문서명, URL, 기준일, 검수·승인 상태를 관리한다.

### 7.4 통화 위험 신호 확보 경로

POC의 우선안은 **참여자 동의 아래 단말 또는 통신 파트너가 통화 내용을 기기 안에서 분석하고, 원문 음성·전사문이 아닌 위험 유형·신뢰도·탐지시각 같은 최소 특징값만 은행 샌드박스에 전달하는 방식**이다. MVP에서는 이 입력을 사전 승인된 합성 특징값으로 대체한다.

- 원문 음성과 전체 전사문은 기본적으로 은행 서버에 전송·저장하지 않는다.
- 단말·통신사 연계가 없는 고객 또는 동의하지 않은 고객에게는 거래 신호만으로 기존 금융회사 확인 절차를 제공하며, 통화 분석이 이뤄진 것처럼 표시하지 않는다.
- POC 착수 전 OS·단말·통신 파트너의 제공 범위, 고객 동의문, 민감정보 해당 여부, 보유기간과 파기 방식을 준법·정보보호 조직이 승인한다.
- 실제 상용화는 제조사·통신사 SDK/API 또는 금융회사와 승인된 신호공유 계약이 확보될 때만 진행한다.

## 8. 사업 모델과 도입 전략

### 8.1 제안 사업 모델

우선 모델은 금융회사가 고객보호 기능으로 도입하고 자사 고객에게 제공하는 B2B2C 방식이다.

- **기관 연간 라이선스(우선 과금 단위)**: 위험 설명·행동안내 모듈, 승인 정책 지식, 평가 리포트
- **구축·연계형**: 금융회사 앱, FDS, 상담 시스템과 기관별 연동
- **운영 고도화**: 시나리오·정책 지식·평가 리포트의 지속 업데이트

실제 과금 방식은 금융회사 POC에서 도입 범위, 호출량, 연계 난이도, 운영 책임을 확인한 뒤 결정한다.

경제성은 `추정 피해예방 기여액 + 상담·민원 처리비 절감액 - (초기 연계 구축비 + 모델 추론비 + 지식 검수비 + 운영·감사비)`로 판단한다. 활성고객·분석건수 과금은 사용량 변동이 큰 기관의 보조 옵션으로 두고, 고객에게 직접 과금하지 않는다.

### 8.2 도입 책임체계

| 역할 | 1차 책임 |
|---|---|
| 사업·고객보호 정책 총괄(Accountable) | 금융소비자보호 조직 |
| 제품·모바일 채널 운영(Responsible) | 디지털채널 조직 |
| 위험 임계값·오탐 관리 | FDS 조직 |
| 개인정보·금지행동·실증 중단 승인 | 정보보호·준법 조직 |
| 피해 안내·이의제기 운영 | 콜센터·피해대응 조직 |

### 8.3 단계별 도입

| 단계 | 목표 | 주요 산출물 | 다음 단계 조건 |
|---|---|---|---|
| MVP | 고객 여정과 설명 방식 검증 | 공개 합성 데모, 정상·위험·피해 시나리오 | 핵심 흐름 재현과 안전 경계 확인 |
| 금융회사 POC | 사용자 행동과 운영 효율 검증 | 샌드박스 데이터, 사용자·상담원 테스트 | 경고 수용·오탐·대응시간 기준 충족 |
| 제한 채널 적용 | 특정 거래·고객군에서 운영성 검증 | 모바일 앱 경고, 상담원 보조화면 | 민원·장애·감사 기준 충족 |
| 기관 확장 | FDS·콜센터·기관 정보공유 연계 | 기관별 정책·권한·영속 감사체계 | 규제·보안·책임 승인 |

### 8.4 제안 POC 운영안

최초 POC는 한 금융회사의 모바일뱅킹 송금 확인 화면과 상담원 보조 화면을 대상으로 하는 8주 제안안이다. 기간과 참여 규모는 기관 승인 과정에서 조정하되, 평가기준은 시작 전에 고정한다.

1. **1~2주차 — 기준 확정:** 고객보호·FDS·디지털채널·정보보호 담당자가 대상 거래, 승인 문구, 금지 행동, KPI 산식을 합의한다.
2. **3~4주차 — 운영자 검증:** 최소 상담원·FDS 담당자 10명과 정상·위험 각 12건 이상의 균형 시나리오로 위험 이유와 행동 안내를 검토한다.
3. **5~6주차 — 사용자 과제:** 탐색적 POC 기준 최소 60명을 위험유형·연령·디지털 숙련도로 층화하고 단순 경고와 설명형 경고를 무작위 비교해 이해도, 재확인, 모의 송금 일시중지 선택을 측정한다. 실제 송금과 실제 사기 상황은 사용하지 않는다. 1~2주차 파일럿 분산을 기준으로 필요한 표본을 다시 산정한다.
4. **7~8주차 — 안전·운영 판정:** 오탐, 금지 권고, 개인정보 노출, 서비스 장애, 상담 증가량을 검토하고 확대·보완·중단을 결정한다.

필요 데이터는 합성 통화 시나리오, 비식별·승인된 거래 특징값, 금융회사 고객보호 정책, 기관 검수를 거친 대응 지식, 정상·위험 라벨, 사용자·상담원 과제 결과다. 실제 원문 통화나 계좌정보는 POC 목적 달성에 필요하고 적법성이 확인된 최소 범위에서만 검토한다.

잠정 성공 가설은 설명형 경고가 단순 경고 대비 모의 공식번호 재확인 선택률을 20%p 이상 높이고, 경고 이유 이해도가 80% 이상이며, 정상 시나리오 오경보율이 단순 경고보다 2%p 넘게 악화되지 않고, 상담원 검토시간을 20% 이상 줄이는 것이다. 이는 확정 성과가 아닌 사전 제안 임계값이며 1~2주차 기준선·표본 산정 후 고객보호책임자가 최종 사전등록한다. 개인정보 노출, 위험한 금융행동 권고, 필수 행동 누락, 감사 불가능한 의사결정은 허용 0건이며 한 건이라도 발견되면 즉시 중단·원인분석 후 재승인한다.

## 9. 사업 가설과 실증 KPI

현재 MVP 자동검사는 구현의 재현성을 확인하는 자료이며 사업 효과를 입증한 결과는 아니다. 실제 도입 타당성은 다음 가설을 POC로 검증한다.

| 지표군 | 핵심 KPI | 기준선·목표 결정 | 측정대상·방법 | 주기·책임자 |
|---|---|---|---|---|
| 사용자 행동 | 모의 송금 일시중지 선택률, 공식번호 재확인 선택률 | 재확인 선택률 +20%p 잠정 가설; 1~2주차 사전등록 | 동일 합성 시나리오 A/B 사용자 과제 | POC 주간·고객보호 조직 |
| 이해·신뢰 | 경고 이해도, 수용률, 행동 선택 정확도 | 이해도 80% 이상 잠정 가설; 2주차 확정 | 과제 성공률과 사후 인터뷰 | 각 실험·UX/디지털채널 조직 |
| 피해 대응 | 1394·긴급 시 112·금융회사·지급정지 안내 도달시간, 절차 완료율 | 기존 안내문 기준선 측정 후 단축 목표 합의 | 피해발생 합성 시나리오 완료시간 | 각 실험·피해대응 조직 |
| 탐지·오탐 | 사기 Recall, Precision, FPR, 정상거래 이탈 | 정상 오경보율 비열등 한계 +2%p 잠정; FDS 승인 | 정상/위험 균형 검증셋·승인 특징값 | 배포 전/주간·FDS 조직 |
| 근거 품질 | 근거 적합률, 공식 지침 일치율 | 전문가 기준선과 승인 임계값을 2주차 확정 | 고객보호·준법 전문가 표본평가 | 지식 변경 시·고객보호/준법 |
| 운영 효율 | 상담원 검토시간, 판정 일치율, 오탐 해제시간 | 검토시간 20% 단축 잠정 가설 | 상담원 태스크·파일럿 운영 로그 | 주간·콜센터/FDS 운영 |
| 안전 | 금지 권고 발생률, 필수행동 누락률, 개인정보 노출 | 치명적 금지 권고·개인정보 노출 허용 0건 | 레드팀 시나리오·감사 로그 | 배포 전/상시·정보보호/준법 |
| 사업 효과 | 추정 피해예방액, 상담 처리비용, 민원 변화 | 실제 파일럿 기준선 확보 후 산식 승인 | POC 전후 비교, 재무·운영 검토 | POC 종료·사업/고객보호 조직 |

구체 목표치는 실제 기준선을 확보한 뒤 금융회사와 합의한다. 현재 합성 데이터 성능을 실사용 성과로 제시하지 않는다.

## 10. 기대 효과

### 금융소비자

- 피해 직전 경고를 이해하고 송금을 재검토할 기회 확보
- 공식 확인과 피해 초기 대응 순서를 빠르게 파악
- 정상상담에 대한 과잉경고와 불필요한 불안이 감소하는지 POC로 검증

### 금융회사

- 기존 FDS 경고의 설명력과 고객 수용성 향상 가능
- 상담원·피해접수 안내의 일관성과 검토 효율 향상 가능
- 피해 예방액, 고객보호 성과, 민원·오탐을 함께 관리할 측정체계 확보
- 변화하는 사기 수법과 정책 지식을 고객 채널에 빠르게 반영

### 사회·산업

- 개인의 주의만 요구하는 방식에서 금융회사와 기관이 함께 책임지는 예방 체계로 전환
- 금융·통신·수사 정보공유 결과를 고객 행동으로 연결하는 접점 마련
- 스미싱, 메신저 피싱, 투자사기 등 유사 금융사기 안내로 확장 가능

## 12. 책임 있는 AI와 운영 원칙

- AI는 위험 설명과 행동 안내를 제공하는 의사결정지원 수단이다.
- 실제 거래 제한·해제, 신고, 지급정지의 권한과 책임은 고객·금융회사·관계기관의 승인 절차에 둔다.
- 위험 판단의 주요 이유와 데이터 기준을 고객·운영자가 확인할 수 있어야 한다.
- 오탐으로 정상 거래가 지연되면 재확인·상담·이의제기 경로를 제공한다.
- 미탐과 신종 수법은 사고 분석과 검증셋 업데이트로 개선한다.
- 개인정보, 보존기간, 접근권한, 감사로그는 실제 도입 금융회사와 규제 기준에 맞춰 설계한다.
- MVP의 합성 데이터와 회귀검사 결과를 실사용 성능으로 오해시키지 않는다.

## 13. MVP에서 확인한 것과 앞으로 검증할 것

### 현재 확인한 범위

- API 키 없이 정상·위험·피해 서비스 여정을 재현하는 공개 데모
- 통화·거래 신호와 위험 이유, 검색 근거, 행동 안내의 한 화면 제시
- 정상상담을 포함한 합성 회귀 시나리오
- 외부 모델 장애나 부적절한 생성 결과가 고객 행동을 통제하지 않도록 하는 안전 경계

### 아직 검증하지 않은 범위

- 실제 고객의 송금 중단률과 경고 수용률
- 실제 금융회사 데이터에서의 오탐·미탐 수준
- 상담원 검토시간과 피해 예방액
- 기관별 레거시 연동, 보안, 개인정보, 감사, 책임분담
- 장기 운영비용과 최종 과금모델
