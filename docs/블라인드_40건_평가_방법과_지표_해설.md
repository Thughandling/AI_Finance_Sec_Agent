
# AI_Finance_Sec 블라인드 40건 평가 방법과 지표 해설

> 작성일: 2026-08-14  
> 목적: 정탐·오탐·미탐 평가가 어떻게 수행되었으며, 각 지표와 결과가 무엇을 의미하는지 설명한다.  
> 중요: 이 평가는 합성 문장 기반의 데모 안정성 평가이며 실제 금융회사 데이터에서의 상용 성능을 의미하지 않는다.

## 1. 먼저 구분해야 할 세 가지 평가셋

현재 프로젝트에는 이름이 비슷하지만 역할이 다른 평가가 존재한다.

| 구분 | 규모 | 용도 | 성능 해석 |
|---|---:|---|---|
| 개발 회귀셋 | 38건 | 이미 발견한 실패를 수정한 뒤 다시 발생하지 않는지 검사 | 알려진 문제에 대한 회귀 방어력 |
| 고정 홀드아웃 | 40건 | 회귀셋과 파일을 분리해 경계·중대 사례를 검사 | 분리 평가이지만 개발 과정에서 결과를 보고 규칙을 수정했으므로 최종 블라인드 성능은 아님 |
| 독립 QA 블라인드셋 | 40건 | 앞의 38건·40건·적대 평가 문구를 사용하지 않고 새 표현으로 일반화 검사 | 당시 엔진의 새로운 표현 대응력을 확인하는 핵심 결과 |

저장된 고정 홀드아웃은 [`evaluation_holdout.json`](../AI_Finance_Sec/public/data/evaluation_holdout.json)이다. 총 40건으로 사기 27건, 정상 13건, Critical 8건으로 구성되어 있다.

독립 QA 블라인드 40건은 QA 에이전트가 기존 파일을 보지 않고 새 범주와 문장으로 실행한 일회성 평가다. 당시 원문 40건 전체가 파일로 저장되지는 않았으며, 혼동행렬과 실패 범주만 검증 기록으로 남았다. 따라서 이 문서에서는 재현 가능한 고정 홀드아웃 결과와, 완전 재현은 불가능하지만 독립성이 더 강한 QA 블라인드 결과를 구분한다.

이후 비판 에이전트가 제공한 별도의 정확한 문장은 [`evaluation_blind_round4.json`](../AI_Finance_Sec/public/data/evaluation_blind_round4.json)에 저장했다. 이 파일은 단일문장 16건, 멀티턴 4건, RAG 5건으로 구성되며 여기서 설명하는 “QA 블라인드 40건”과는 다른 평가다.

## 2. 블라인드 40건을 진행한 이유

초기 엔진은 8개의 쉬운 합성 문장에서 100%에 가까운 결과를 보였다. 그러나 문장에 사용된 단어가 탐지 규칙의 단어와 거의 같아 다음 문제를 확인할 수 없었다.

- 새로운 기관·직책·앱·자산 이름이 등장하는 경우
- 같은 위험행동을 다른 말로 표현하는 경우
- 뉴스·교육·신고 목적으로 사기 문장을 인용하는 정상 사례
- “하지 않았다”와 “하라고 요구했다”가 한 문장에 섞인 경우
- 정상적인 본인 계좌·공식 앱 사용
- 여러 대화 턴에 위험 정보가 나뉘어 나타나는 경우
- 이미 현금·수표·인증정보·원격권한 등을 넘긴 피해 완료 사례

따라서 알려진 회귀셋을 통과한 엔진에 전혀 다른 표현을 입력해, 암기한 표현이 아니라 위험의 구조를 판단하는지 검사했다.

## 3. 평가 절차

### 3.1 기존 데이터와 표현 분리

QA 에이전트는 다음 파일의 문장을 그대로 재사용하지 않았다.

- `evaluation_cases.json` 38건
- `evaluation_holdout.json` 40건
- 2·3차 적대 평가 문장

새 문장은 사기 20건과 정상 20건으로 균형 있게 만들었다. 실제 발생률을 재현하기 위한 표본이 아니라, 사기 탐지와 정상 보호 능력을 같은 비중으로 공격하기 위한 스트레스 테스트다.

### 3.2 새로 투입한 범주

기존 정규식의 단순 동의어만 바꾸지 않고 다음과 같은 새로운 행위 구조를 포함했다.

| 평가 영역 | 예시 범주 |
|---|---|
| 기관 사칭 | 관세청, 건강보험공단, 통신사, 우체국 등 기존에 없던 기관 |
| 기업 사칭 | 회계·구매 부서, 변경 수취처, 대금 집행 요구 |
| 지인·권위자 사칭 | 교장, 성직자 등 새로운 직책 |
| 인증정보 탈취 | 보안카드, 승인번호, 인터넷뱅킹 암호 |
| 원격 통제 | QuickSupport, RustDesk, 화면 권한 허용 |
| 투자·관계형 사기 | 해외선물, 로맨스 스캠 |
| 피해 완료 | 자기앞수표 전달, 면허증·암호 전송, 원격권한 제공 |
| 정상 Hard Negative | 본인 주도 거래, 기업 내부 승인, 공식 앱, 명시적 거부·미실행 |
| 멀티턴 | 정정, 새 주제, 점진적 유도, 교육 예문 뒤 실제 위험 요구 |

### 3.3 두 엔진에 동일 입력

같은 40개 문장을 다음 두 경로의 탐지 함수에 입력했다.

1. 브라우저 Mock용 TypeScript 엔진: `app/lib/engine.ts`
2. FastAPI/LangGraph용 Python 엔진: `backend/app/graph.py`

각 문장에 대해 다음을 비교했다.

- 예상 라벨: `fraud` 또는 `normal`
- 실제 라벨: `사기` 또는 `정상`
- 위험점수와 위험등급
- 위험유형
- TypeScript와 Python의 결과 일치 여부

### 3.4 혼동행렬 집계

평가 결과를 다음 네 종류로 분류했다.

| 구분 | 의미 | 데모 관점 |
|---|---|---|
| TP, 정탐 | 실제 사기 문장을 사기로 탐지 | 위험을 올바르게 경고 |
| TN, 정상 정탐 | 실제 정상 문장을 정상으로 판단 | 불필요한 공포와 거래 방해를 방지 |
| FP, 오탐 | 정상 문장을 사기로 판단 | 정상 고객에게 불필요한 경고 발생 |
| FN, 미탐 | 사기 문장을 정상으로 판단 | 가장 위험한 실패로, 거짓 안전을 제공할 수 있음 |

## 5. 각 평가지표의 의미와 계산

### 5.1 Accuracy — 전체 정확도

전체 문장 중 맞힌 비율이다.

`Accuracy = (TP + TN) / 전체 = (2 + 18) / 40 = 0.50`

결과는 50%다. 하지만 보이스피싱처럼 사기 미탐 비용이 큰 문제에서는 Accuracy만 보면 안 된다. 정상 18건을 맞힌 결과가 사기 18건을 놓친 문제를 가릴 수 있기 때문이다.

### 5.2 Precision — 사기 경고의 적중도

엔진이 사기라고 경고한 문장 중 실제 사기였던 비율이다.

`Precision = TP / (TP + FP) = 2 / (2 + 2) = 0.50`

사기 경고 두 번 중 한 번만 맞았다는 의미다. Precision이 낮으면 경고 피로, 정상거래 이탈, 민원 가능성이 커진다.

### 5.3 Fraud Recall — 실제 사기를 잡아낸 비율

실제 사기 문장 중 엔진이 사기로 잡아낸 비율이다.

`Recall = TP / (TP + FN) = 2 / (2 + 18) = 0.10`

결과는 10%로, 새로운 사기 표현 20건 중 18건을 놓쳤다. 이 서비스에서는 가장 중요한 지표 중 하나다. 미탐은 사용자에게 “강한 사기 징후 없음”이라는 잘못된 인상을 줄 수 있기 때문이다.

### 5.4 FPR — 정상 문장을 사기로 잘못 경고한 비율

실제 정상 문장 중 사기로 잘못 분류한 비율이다.

`FPR = FP / (FP + TN) = 2 / (2 + 18) = 0.10`

결과는 10%다. 정상 사용자 10명 중 1명꼴로 잘못 경고할 수 있다는 뜻이다. 데모 목표 기준은 5% 이하로 두었다.

### 5.5 Specificity — 정상을 올바르게 보호한 비율

실제 정상 문장을 정상으로 맞힌 비율이다.

`Specificity = TN / (TN + FP) = 18 / 20 = 0.90`

90%로 정상 문장 판별은 상대적으로 높았다. 그러나 높은 Specificity가 낮은 Fraud Recall을 보상하지는 않는다.

### 5.6 F1 — Precision과 Recall의 균형

Precision과 Recall의 조화평균이다.

`Fraud F1 = 2 × Precision × Recall / (Precision + Recall)`  
`= 2 × 0.50 × 0.10 / 0.60 ≈ 0.167`

사기 F1은 약 16.7%다. 경고 적중도와 사기 포착률을 동시에 만족하지 못했다는 뜻이다.

### 5.7 Macro F1 — 사기와 정상을 동일하게 중요하게 본 평균

사기 클래스 F1과 정상 클래스 F1을 각각 구한 뒤 단순 평균한다.

- 사기 F1: 약 16.7%
- 정상 F1: 약 64.3%
- `Macro F1 = (16.7% + 64.3%) / 2 ≈ 40.5%`

정상 표본이 많거나 적어도 두 클래스를 동일한 비중으로 평가할 수 있다. 이번 결과 40.5%는 한쪽 클래스만 잘 맞히는 편향이 크다는 의미다.

### 5.8 Critical Recall — 반드시 잡아야 하는 중대 사례

일반 Recall과 별도로, 놓치면 피해 대응이 지연되는 사례를 Critical로 관리한다. 이번 신규 Critical 3건은 다음과 같은 피해 완료 유형이었다.

- 자기앞수표 전달
- 운전면허증과 인터넷뱅킹 암호 전송
- RustDesk 화면 권한 허용

세 건 모두 피해 완료로 탐지하지 못해 `Critical Recall = 0 / 3 = 0%`였다. 피해 완료로 판단되지 않으면 1394, 긴급 시 112, 금융회사 지급정지 요청 안내도 시작되지 않는다.

### 5.9 TypeScript↔Python Parity — 두 실행경로의 일관성

같은 문장을 브라우저 Mock과 FastAPI 실제 경로에서 동일하게 판정하는지를 확인한다.

이번 결과는 `40 / 40 = 100%`였다. 이는 두 엔진이 서로 다르게 행동하는 문제는 없다는 뜻이다. 다만 두 엔진이 같은 잘못된 판정을 내릴 수도 있으므로 정확도 자체를 증명하지는 않는다.

## 6. 어떤 실패가 발견됐는가

### 6.1 새로운 사기 표현 미탐

관세청·통신사·우체국 사칭, 새로운 BEC, 보안카드, QuickSupport/RustDesk, 자기앞수표·면허증 피해 등 기존 단어 목록에 없는 표현을 대부분 정상으로 판단했다.

### 6.2 점진적 멀티턴 미탐

한 번에 “송금하세요”라고 말하지 않고 여러 턴에 걸쳐 공무원 사칭 → 체납 사건 → 확인용 계좌 → 전액 이동으로 유도하면 핵심 행위가 누적되지 않았다.

### 6.3 정상 문장의 오탐

범죄예방 수업에서 납치·현금 요구 음성을 들은 경우와, 택배 링크를 누르지 않았다고 명시한 문장을 위험으로 판단했다. 이는 인용·교육·명시적 거부의 범위를 정확히 이해하지 못한 결과다.

### 6.4 분류 오류의 RAG 전파

RAG 자체의 무관 질문 차단과 정책 fallback은 동작했다. 그러나 앞단이 새로운 위험을 정상으로 분류하면 `정상 절차` 문서를 검색하므로 잘못된 분류가 안내 근거까지 전파된다.

## 7. 합격 기준과 판정

프로젝트에서 제안한 독립 평가 합격 기준은 다음과 같다.

| 지표 | 합격 기준 | 블라인드 40건 | 판정 |
|---|---:|---:|---|
| Fraud Recall | ≥95% | 10.0% | 실패 |
| FPR | ≤5% | 10.0% | 실패 |
| Macro F1 | ≥92% | 40.5% | 실패 |
| Critical Recall | 100% | 0% | 실패 |
| TS↔Python Parity | 100% | 100% | 통과 |

따라서 알려진 회귀셋의 자동검사가 통과하더라도 독립 QA 기준으로는 명확한 실패다. 당시 엔진을 완료 또는 고정 모델로 판단하지 않았다.

## 8. 평가 결과가 설계에 미친 영향

블라인드 결과는 정규식에 기관명·앱명·자산명 동의어를 계속 추가하는 방식의 한계를 보여줬다. 이후 구조는 다음 방향으로 전환 중이다.

1. Qwen을 자유 답변 생성기가 아니라 구조화 위험 판정 보조기로 사용한다.
2. 외부 행위자, 요구 자산, 행동 극성, 목적지, 완료 여부, 정상 문맥, 근거 구간을 JSON으로 받는다.
3. 규칙과 모델이 불일치하거나 신뢰도가 낮으면 `안전`으로 단정하지 않고 최소 `주의`로 처리한다.
4. 멀티턴은 최근 문장 단순 결합 대신 활성 사건, 정정, 종료, 피해 완료 상태를 관리한다.
5. RAG는 판정된 위험유형과 맞지 않는 문서가 Top-1이 되지 않도록 제한하고, 근거가 약한 경우 `policy_fallback`임을 구분한다.
6. 생성형 모델의 자유문은 계속 고객 화면에 직접 노출하지 않고 승인 정책 문장만 최종 안내로 사용한다.

## 9. 결과를 발표할 때의 정확한 표현

사용 가능한 표현:

> 기존 회귀셋에서는 알려진 실패를 재발하지 않도록 자동검사를 구성했지만, 새로운 40개 합성 블라인드 문장에서는 Fraud Recall 10%, FPR 10%, Macro F1 40.5%로 일반화 한계를 확인했다. 이 결과를 근거로 단순 키워드 규칙 확장을 중단하고 구조화 LLM 판정과 사건 State 기반 결합 구조로 전환했다.

사용하면 안 되는 표현:

- “모델 정확도 100%”
- “40건 홀드아웃을 모두 통과했으므로 실제 사기를 모두 탐지한다”
- “실제 금융거래에서 피해 예방 효과가 입증됐다”
- “RAG Top-1 100%이므로 답변도 항상 정확하다”

## 10. 재현성과 남은 과제

- 고정 회귀셋과 고정 홀드아웃은 저장되어 자동 재현할 수 있다.
- QA 블라인드 40건의 정확한 원문 전체는 당시 별도 파일로 저장되지 않아 결과의 완전 재현에는 한계가 있다.
- 이후 모든 독립 QA 문장은 평가 직후 별도 버전 파일로 동결해야 한다.
- 구조화 Qwen 판정 구현 후에는 기존 파일과 겹치지 않는 새로운 블라인드셋으로 다시 평가해야 한다.
- 실제 서비스 성능 주장은 금융회사 승인 데이터와 사전등록된 평가 설계에서 별도로 검증해야 한다.
